## 1. 变量与密钥清单

`ci.yml` 的 `deploy` job 读取这些值。**注意 vars 与 secrets 的划分不要混**：

| 类型 | 名称 | 示例值 | 说明 |
| --- | --- | --- | --- |
| var | `DEPLOY_ENABLED` | `true` | 开关。为 `true` 且推送到 main 才会触发部署 |
| secret | `DEPLOY_HOST` | `1.2.3.4` 或 `srv.example.edu.cn` | 目标机地址。**`ci.yml` 读的是 secret**，放 var 不生效 |
| secret | `DEPLOY_USER` | `ubuntu` / `root` | SSH 用户。**同样读的是 secret** |
| var | `DEPLOY_PATH` | `/opt/campus-overflow` | 目标机上存放 `docker-compose.yml` 与 `.env` 的目录 |
| var | `DEPLOY_PORT` | `22` | SSH 端口，不填默认 22 |
| var | `DEPLOY_URL` | `https://co.example.edu.cn` | 部署后写进 run 的 environment url，便于直接点开 |
| secret | `DEPLOY_SSH_KEY` | `-----BEGIN OPENSSH PRIVATE KEY-----...` | **私钥**，对应的公钥要加到目标机 `~/.ssh/authorized_keys` |

> **为什么这样分**：以 `ci.yml` 的实际读取为准——`deploy` job 里 `host` / `username` / `key`
> 三项都写的是 `secrets.*`，只有 `DEPLOY_ENABLED` / `DEPLOY_PATH` / `DEPLOY_PORT` / `DEPLOY_URL`
> 用的是 `vars.*`。文档与 workflow 必须一致，否则「按文档配完却连不上」是最难查的一类问题。
> 如果确实希望 HOST / USER 放 var（UI 里更好改），需要**同时改 `ci.yml`** 的对应行，不能只改文档。
> **不要把私钥写进 var**，也不要把私钥提交进仓库。

## 2. 一键配置（GitHub CLI）

在**有 Admin 权限**的账号下执行。`gh` 已登录的前提下：

```bash
REPO=hbuas-se-2026fall/cs2412-team05-campus-overflow

# 变量
gh variable set DEPLOY_ENABLED --repo $REPO --body "true"
gh secret set DEPLOY_HOST      --repo $REPO --body "<服务器地址>"
gh secret set DEPLOY_USER      --repo $REPO --body "<ssh 用户>"
gh variable set DEPLOY_PATH    --repo $REPO --body "/opt/campus-overflow"
gh variable set DEPLOY_PORT    --repo $REPO --body "22"
gh variable set DEPLOY_URL     --repo $REPO --body "https://<域名>"

# 密钥（从本地文件读，不落进 shell 历史）
gh secret set DEPLOY_SSH_KEY --repo $REPO < ~/.ssh/deploy_key
```

没有 `gh` 时用网页：`Settings → Secrets and variables → Actions`，分别建 **Variables** 与 **Secrets**。

## 3. 服务器侧准备（一次性）

```bash
# 1) 装 Docker 与 compose 插件（Ubuntu 示例）
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER   # 重新登录生效

# 2) 建部署目录，放 compose 与 .env
sudo mkdir -p /opt/campus-overflow && sudo chown $USER /opt/campus-overflow
cd /opt/campus-overflow
# compose 文件由首次部署时 pull 下来，或用 scp 从仓库拷贝一份

# 3) 写 .env（不要提交进仓库）
cat > .env <<'EOF'
BACKEND_IMAGE=ghcr.io/hbuas-se-2026fall/cs2412-team05-campus-overflow-backend:latest
WEB_IMAGE=ghcr.io/hbuas-se-2026fall/cs2412-team05-campus-overflow-web:latest
SPRING_PROFILES=prod
MYSQL_ROOT_PASSWORD=<强密码>
CO_FIELD_KEY=<32 字节随机串>
EOF

# 4) 开放端口：80（前端）、8080（后端直连调试）、3000/9090（监控，按需）
```

**注意 `SPRING_PROFILES=prod`**：compose 默认是 `prod,demo`，`demo` 会写入演示数据（见
`final-delivery-checklist.md` §7 K2），正式环境必须显式覆盖成 `prod`。

## 4. 触发与验收

`main` 受 CODEOWNERS 保护，**不能直推**；而 `deploy` job 只认 `main` 的 push 事件。
实际路径是：把 `develop` 合并进 `main` 的那个 PR 被合并时，push 事件即触发部署。

```
合并一个 develop → main 的 PR（例如 PR #68）后，main 的 push 会自动跑 deploy job
```

跑完后按顺序核对：

| # | 检查 | 期望 |
| --- | --- | --- |
| 1 | Actions → `deploy` job 状态 | success（不是 skipped） |
| 2 | job 里「部署后冒烟测试」步骤 | 输出 `/actuator/health/readiness` 为 UP、`GET /` 200、`GET /api/v1/questions` 200 |
| 3 | `DEPLOY_URL` 在浏览器打开 | 能登录、能提问 |
| 4 | 服务器上 `docker compose ps` | 4 个容器 running / healthy |
| 5 | 截图 | Actions 成功页 + 线上首页 + 登录后页面，存进 `docs/verification/` |

## 5. 常见失败与排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `deploy` 一直 skipped | `DEPLOY_ENABLED` 不是 `true`，或不是推送到 main | 检查变量与触发分支 |
| `Permission denied (publickey)` | 私钥与目标机 `authorized_keys` 不匹配，或用户错 | 用同一个用户手动 ssh 验证 |
| 容器起来又退出，日志 `Unable to access jarfile` | 镜像里没有 jar（历史上 `COPY --from` 空 glob 导致） | 用 `.github/workflows/stack-smoke.yml` 的「校验镜像内容」步骤确认；该 bug 已由 #67 修复 |
| 首页 404 / 刷新后 404 | Nginx 缺 SPA fallback | 检查 `deploy/nginx.conf` 的 `try_files` |
| 健康检查一直 unhealthy | 数据库没起来或 profile 错 | 看 `docker compose logs backend`，确认 `.env` 里 DB 连接 |
| 端口冲突 | 目标机已有 80/8080 | 改 compose 端口映射或清理占用 |

## 6. 没有服务器时的降级方案（**不能当作已上线**）

| 方案 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| `.github/workflows/stack-smoke.yml`（已落地） | 编排能起来、四个容器 healthy、前后端与监控栈可访问 | 不是常驻服务，没有对外 URL |
| 本地 `docker compose up` | 同上，且可现场演示 | 依赖本机 Docker |
| 临时公网隧道（如 cloudflared / ngrok） | 系统可通过公网访问 | URL 随运行结束失效，不是「线上系统」 |

**报告措辞建议**：以上三者都写成「部署可运行性已验证」，不要写成「已上线」。Lab 8 的
「可访问线上 URL」一项，只有在有常驻服务器且 URL 长期可访问时才勾。
