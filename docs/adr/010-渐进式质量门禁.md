# ADR-010：渐进式质量门禁（SPRINT_MODULES）

**状态**：已接受 ｜ **驱动特征**：可持续交付、反馈速度（V3 指导书第 8.2 节要求）

## 背景

Sprint0 起始代码的 CI（`.github/workflows/ci.yml`）在每次 push / PR 都执行**全量** `mvn verify`（compile → test → verify，含集成测试与覆盖率）。随着 Sprint1 起各限界上下文（identity / qa / reputation / discovery）被不同小组并行开发，全量验证存在两个问题：

1. **反馈慢**：任何一次 PR 都要跑完所有模块（含集成测试的 Testcontainers MySQL/Redis 启动），高频小步提交下等待时间过长；
2. **门禁失焦**：一次小改动也要承受所有模块的失败风险，红叉与改动本身无关时，团队成员容易对 CI 产生"狼来了"疲劳，反而削弱门禁权威性。

同时，课程要求 CI 必须是**质量门禁**而非摆设：任何"改断言/删测试/@Disabled 求绿"都属于红线行为（详见《协作指南》红线条款）。因此需要在**保证门禁强度**的前提下缩短反馈回路。

## 决策

采用**渐进式质量门禁**，按 Sprint 调整测试运行范围：

1. **按 Sprint 缩小运行范围**：在 CI 中通过 `SPRINT_MODULES`（如 `-pl co-identity,co-shared-kernel,co-bootstrap -am`）只构建与测试**当前 Sprint 相关模块**及其依赖，`SPRINT_MODULES` 由各 Sprint 的交付范围决定并记录在仓库（建议维护于 `docs/` 或 workflow 顶层变量）。
2. **S3 恢复全量 `mvn verify`**：从 Sprint3 起，集成测试（failsafe）与覆盖率成为**硬门禁**，CI 在 `backend` 目录执行完整 `mvn -B verify -Djacoco.skip=false`，确保跨上下文集成稳定后再收口。
3. **ci.yml 每次改动须 PR 评审**：CI 配置属于共享基础设施，任何对 `.github/workflows/ci.yml` 的修改都通过普通 PR（≥1 非作者 Approve）合并，禁止直接推送 main/develop；同时勾选"必须通过状态检查"（分支保护规则要求），避免"悄悄放宽门禁"。
4. **门禁红线不变**：渐进式门禁**只允许缩小运行范围**，禁止通过 `-Dmaven.test.failure.ignore=true`、`@Disabled`、删除测试或修改已有断言来"变绿"。

## 后果

- 正面：Sprint1/Sprint2 期间每次 PR 的验证范围与改动相关，反馈更快；门禁权威性在 S3 收口前逐步建立；CI 配置变更受到与业务代码同等评审约束。
- 负面：缩小范围意味着某些跨模块回归在 S1/S2 不会被自动发现，需要靠 PR 描述中的测试证据与人工评审兜底；S3 收口后全量集成测试的耗时增加，需接受该成本。
- 演进：若某 Sprint 新增模块，需同步更新 `SPRINT_MODULES`；若部署流水线（images/deploy）依赖某模块产物，缩小范围时必须保证该模块仍在构建列表内（`co-bootstrap` 默认保留）。

## 被否决的替代方案

- **维持全量 verify 不变**：门禁最强，但 S1/S2 高频提交下反馈太慢，且未完成模块的失败会干扰已完成模块的合并，实际执行中团队容易绕过。
- **完全禁用集成测试直到 S3**：反馈最快，但门禁强度为零，不符合"渐进式门禁"的课程要求，也埋下 S3 一次性收口的大回归风险。
- **按开发者/团队拆分 CI 文件**：可读性差、维护成本高，且无法解决"改动无关的红叉"问题。
